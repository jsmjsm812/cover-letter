자기소개서

01

지원동기

게임을 만드는 사람이 되고 싶다는 생각은 오래전부터 있었지만, 막연한 관심을 실제 개발 역량으로 바꾸는 데에는 시간이 필요했습니다. 청운대학교에서 멀티미디어학과를 복수전공하며 화면 속 콘텐츠를 직접 설계하고 구현하는 즐거움을 알게 되었고, 이를 게임이라는 형태로 확장하고자 넥스트러너스 게임개발 초격차 캠프에 진학했습니다.

캠프에서는 두 편의 팀 프로젝트를 팀장 겸 기획·클라이언트 개발자로 완주했습니다. 2인 4주 프로젝트인 LAST GLADIATOR에서는 게임의 초기 스코프를 패링 중심의 근접 전투와 6개 스테이지로 축소하고, 전투 규칙부터 적 AI와 데이터 구조까지 직접 설계했습니다. 이후 5인 프로젝트인 위치 크로니클에서는 라이프 시스템을 담당하며 파밍·낚시·연금술을 하나의 흐름으로 연결하고, 67종의 스킬 데이터와 200종 이상의 라이프 아이템을 관리할 수 있는 구조를 구축했습니다. 캠프를 마친 뒤에는 개인 프로젝트로 모바일 로그라이트 타워디펜스 ‘작은 왕국’을 기획부터 개발·아트·밸런싱까지 혼자 완주하며, 팀에서 맡았던 역할의 범위를 스스로 넓혀보는 경험을 쌓았습니다.

이어서 5인 팀 프로젝트 ‘용사 때문에 레벨업’에서는 마왕 성장 시스템(스킬·특성·증강·시너지)과 밸런스, 인게임 연출을 맡았습니다. 혼자 만들 때와 달리 팀원이 만드는 그리드·전투 시스템과 맞물려 돌아가도록 만드는 것이 핵심 과제였고, 6주 동안 저장소 기준 PR 19개로 제 작업을 팀 코드에 통합했습니다. 이 게임은 2026년 11월 6일 STOVE에 출시했습니다.

네 프로젝트를 경험하며 제가 가장 몰입하는 순간은 단순히 기능을 구현했을 때가 아니라, 기획한 경험이 실제 플레이에서 의도한 대로 느껴지도록 시스템을 설계하고 다듬을 때라는 것을 알게 되었습니다.

저는 Unity 클라이언트 개발자로서 기능 하나를 만드는 데 그치지 않고, 게임의 규칙과 데이터를 이해하고 그것을 실제 플레이 경험으로 연결할 수 있는 개발자가 되고 싶습니다.

02

성장과정

처음부터 게임 개발자를 꿈꿨던 것은 아닙니다. 청운대학교에서 호텔조리식당경영학과와 멀티미디어학과를 복수전공하며 서로 다른 분야에서 문제를 해결하는 방식을 배웠습니다.

조리에서는 정해진 재료와 시간 안에서 일정한 결과를 만들어내는 것이 중요했습니다. 이 경험은 개발에서도 비슷하게 이어졌습니다. LAST GLADIATOR에서는 4주라는 제한된 일정에 맞춰 초기의 오픈 필드·다수 무기·성장 시스템 계획을 버리고 패링 중심의 근접 전투와 6개 스테이지로 범위를 줄였습니다. 팀장으로서 이 결정을 팀에 설득하고 실제 데모까지 완성했습니다.

지금의 저는 새로운 기술 자체를 많이 아는 것보다, 주어진 상황에서 필요한 기술을 선택하고 실제 결과물로 연결하는 개발자가 되는 것을 중요하게 생각합니다.

03

문제 해결과 협업

제가 개발하면서 가장 중요하게 생각하는 것은 문제를 발견했을 때 원인을 구조적으로 파악하고, 다시 같은 문제가 발생하지 않는 방식으로 해결하는 것입니다.

LAST GLADIATOR · 적 AI 구조 결정
적 AI를 처음 설계할 때는 Unity의 Behavior Tree를 사용하려 했습니다. 하지만 4주라는 일정을 고려했을 때 학습·구현 비용이 크다고 판단해, 하루 동안 프로토타입을 만들어 확인한 뒤 15-state FSM으로 방향을 전환했습니다. Hit·Stun 같은 인터럽트가 끝난 뒤 이전 상태로 복귀하도록 InterruptStack을 별도로 구성했습니다.

위치 크로니클 · 오프라인 정산
매 프레임 타이머 방식이 앱 강제 종료·절전 상황에서 저장 시점에 의존하는 문제가 있어, DateTime 기반 오프라인 정산 방식으로 바꿔 100일 방치·시간 조작 같은 예외도 Clamp로 안전하게 처리했습니다.

작은 왕국 · 웨이브가 끝나지 않는 버그
웨이브가 끝났는데도 게임이 멈추는 버그가 있었는데, 원인은 유니티 코루틴이 오브젝트가 비활성화되면 콜백을 호출하지 않고 조용히 멈춘다는 특성이었습니다. 생존 개체 수를 ‘사망 애니메이션이 끝나는 시점’에 줄이도록 짜여 있어서, 그 애니메이션이 끝까지 재생되지 않으면 카운트가 영원히 0이 되지 않았습니다. 판정(생존 여부)과 연출(애니메이션 재생)은 수명이 다른 값이라는 것을 깨닫고, 판정은 죽음이 확정되는 즉시 처리하고 연출은 그와 무관하게 나중에 재생되도록 분리해 해결했습니다.

용사 때문에 레벨업 · 팀원 코드와의 접점
웨이브 클리어 배너가 결과창·보상 카드와 동시에 뜨는 문제가 있었습니다. 스테이지 진행은 팀원이 만든 비동기 상태 머신이 맡고 있어서, 제가 만든 연출 코드로는 순서를 맞출 방법이 없었습니다. 팀원 코드를 고쳐 쓰는 대신 배너 쪽에 TaskCompletionSource 기반의 대기 지점을 만들고, 진행 코드의 세 곳(결과창 직전·보상 카드 직전·용사 스폰 직전)에 대기 호출 한 줄씩만 넣었습니다. 배너가 없거나 꺼져 있으면 즉시 통과하고 취소 토큰도 그대로 따르게 해서, 팀원의 흐름은 바꾸지 않고 연출만 얹었습니다.

협업에서는 사람이 계속 맞춰야 하는 구조보다, 서로의 작업이 자연스럽게 분리되는 구조를 만드는 것을 중요하게 생각합니다. 위치 크로니클에서는 GitHub PR을 기준으로 시스템 단위 작업을 관리하고, 파일 소유권 규칙을 팀 위키에 정리했습니다. 용사 때문에 레벨업에서는 성장 시스템을 순수 C# 클래스와 인터페이스로 분리해 팀원의 씬이 완성되기 전에 샌드박스에서 먼저 검증했고, 팀원 파일은 읽기만 하며 꼭 필요한 연결 지점만 명시해서 넣었습니다. 그 덕분에 실전투로 옮길 때 성장 시스템의 핵심 코드는 거의 바뀌지 않았습니다.

04

본인의 강점

첫째

제한된 시간 안에서 우선순위를 판단하고 결과를 만들어냅니다.

두 프로젝트 모두 팀장으로 참여하면서 가장 많이 고민했던 것은 “무엇을 더 만들 것인가”보다 “무엇을 지금 만들지 않을 것인가”였습니다.

둘째

데이터 주도 설계를 선호합니다.

LAST GLADIATOR의 EnemyStageData, 위치 크로니클의 스킬 SO 67종에 이어, 작은 왕국에서는 수호자 10종·침입자 8종의 스탯과 특수효과를 전부 ScriptableObject로 분리하고, 씬 구성과 아트 임포트까지 자동화하는 에디터 메뉴 58개를 직접 만들어 혼자서도 반복 작업 없이 콘텐츠를 확장할 수 있는 파이프라인을 구축했습니다. 용사 때문에 레벨업에서는 스킬 19종·증강 30종·특성 40노드를 같은 방식으로 데이터화하고, 밸런스 시트에서 에셋과 테스트 씬을 생성하는 도구와 전투 시뮬레이터로 수치를 조정했습니다.

셋째

플레이어가 직접 느끼는 부분을 중요하게 생각합니다.

0.2초 패링 판정, 낚시 텐션, 연금술의 정확 일치 판정처럼 규칙을 플레이어가 예측할 수 있도록 만드는 것에 집중했습니다.

넷째

AI 도구를 생산성 있게 활용하되 검증은 직접 합니다.

작은 왕국과 용사 때문에 레벨업은 Claude Code를 페어 프로그래밍 도구로 적극 활용해 개발했습니다. 용사 때문에 레벨업 저장소에서 제가 올린 커밋 102개(머지 제외) 중 98개에 AI 공동 작성 표기가 남아 있습니다. 기획 결정, 플레이 테스트를 통한 검증, 밸런스 방향 판단은 전부 직접 했고, AI에게는 구현과 코드베이스 전수 검색 같은 반복적·정적인 작업을 맡겼습니다. AI가 맥락이 끊기면 이미 걷어낸 기능을 다시 제안하는 것을 겪은 뒤로는, 핵심 결정을 CLAUDE.md에 고정해두고 참조하게 했습니다. 팀 프로젝트에서는 AI가 팀원의 코드를 임의로 고치지 않도록 읽기만 허용했습니다.

도구를 쓰는 것과 결과물을 책임지는 것은 다른 문제라고 생각하며, 최종 검증은 항상 실제 플레이로 직접 확인합니다.
